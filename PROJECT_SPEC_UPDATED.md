# Photography Website Project Specification

## 1. Project Overview

Build a personal photography website that allows photographs to be uploaded from a computer, stores the actual image files in Cloudinary, stores photo metadata and keywords in PostgreSQL, and displays the photographs through a responsive Tailwind CSS web interface.

The website will use keywords already assigned in Adobe Lightroom Classic. These keywords will be read automatically from exported image metadata when photographs are uploaded.

The application will not initially provide a separate keyword-management system. Lightroom Classic will be the primary source of truth for photographic keywords.

The system will be hosted on Railway.

---

## 2. Main Goals

The application should:

1. Display a clean, modern photographic portfolio.
2. Allow photographs to be filtered using Lightroom keywords.
3. Allow photographs to be uploaded easily from a desktop computer.
4. Automatically extract Lightroom keywords from uploaded photographs.
5. Store photo metadata and keyword relationships in PostgreSQL.
6. Store and serve image files using Cloudinary.
7. Use Cloudinary for image resizing, optimisation and thumbnails.
8. Be simple enough to understand and maintain.
9. Use a technology stack consistent with my existing web projects.
10. Be designed so Cloudinary could later be replaced by another S3/object-storage service without major changes to the application.

Photographs intended for the website should be exported from Lightroom with metadata included.

The export should preserve:

- capture date
- title where available
- caption/description where available
- Lightroom/IPTC keywords
- keyword hierarchy if available

Website image dimensions can initially be relatively large because Cloudinary will generate smaller display versions.

Example:

```text

Colour space: sRGB
Include metadata: yes

```

The exact Lightroom export preset can be defined separately.

## 6. Keyword Philosophy

Lightroom is the primary source of truth for keywords.

For example:

```text
Subject
├── Architecture
├── Landscape
├── People
├── Street
└── Abstract

Place
├── UK
│   ├── Leicester
│   ├── London
│   └── Cornwall
└── France
    └── Paris

Style
├── Black and White
├── Minimal
└── Abstract

Time
├── Day
├── Night
├── Sunrise
└── Sunset
```

A photograph could therefore contain:

```text
Subject > Street
Place > UK > Leicester
Style > Black and White
Time > Night
```

The application should preserve enough information to support hierarchical keyword filtering later.

Initially, however, the public interface can display selected leaf keywords such as:

```text
Street
Leicester
Black and White
Night
```

## 10. Separation of Image Storage

Cloudinary-specific functionality should be isolated.

For example:

```text
app/services/cloudinary_service.py
```

This service should provide functions similar to:

```python
upload_photo(file)

delete_photo(public_id)

get_thumbnail_url(public_id)

get_gallery_url(public_id)

get_large_url(public_id)
```

The rest of the application should not need to know how Cloudinary works.

This will allow Cloudinary to be replaced later by:

- Railway Storage Buckets
- Cloudflare R2
- Amazon S3
- Backblaze B2

without substantially changing the application.

## 12. Keyword Import

When an uploaded photograph contains keywords:

```text
Leicester
Street
Night
Architecture
```

the application should:

1. Normalise each keyword.
2. Check whether the keyword already exists.
3. Create it if necessary.
4. Associate it with the photograph.

Do not create duplicate keywords because of case differences such as:

```text

Street

```

The display name may remain:

```text
Street
```

while its slug is:

```text

```

## 45. Lightroom Keyword and Website Category Logic

### Design Principle

Keep Lightroom Classic as simple as possible.

Lightroom should contain **one flat set of descriptive keywords only**. Do not require separate Lightroom categories, keyword groups, or website-specific classifications.

Example Lightroom keywords:

```text
Street
Architecture
Landscape
People
Leicester
London
Night
Black and White
Minimal
Historic
```

These keywords are assigned normally in Lightroom Classic and embedded into exported JPEG metadata.

### Website Interpretation

The website imports the Lightroom keywords from IPTC/XMP metadata and stores them in PostgreSQL.

The website then decides which imported keywords should be promoted to **primary categories**.

For example:

```python
PRIMARY_CATEGORIES = [
    "Street",
    "Architecture",
    "Landscape",
    "People",
]
```

All other imported Lightroom keywords remain available as **secondary filters**.

This means Lightroom does not need to know anything about the website navigation structure.

### Example

A photograph may contain these Lightroom keywords:

```text
Architecture
Leicester
Night
Black and White
Historic
```

The website interprets them as:

```text
Primary category:
Architecture

Secondary filters:
Leicester
Night
Black and White
Historic
```

A user can therefore browse `Architecture` and then refine the selection using keywords such as `Leicester`, `Night`, or `Black and White`.

### Dynamic Secondary Filters

After a primary category is selected, the website should preferably show only secondary keywords that actually occur in photographs within that category.

Example:

```text
Architecture

Available filters:
Leicester
London
Night
Black and White
Historic
Modern
```

This keeps the interface uncluttered even if Lightroom eventually contains many keywords.

### Multiple Filters

Secondary filters should support combinations.

Example:

```text
Architecture + Leicester + Night
```

The initial filtering rule should use **AND logic**:

> Show photographs containing all selected keywords.

### Website-Only Fields

Some information belongs to the website rather than Lightroom and should remain separate database fields.

Examples:

```text
published
featured
homepage
hidden
sort_order
```

These are presentation or administration states, not descriptive photographic keywords.

### Source of Truth

The system should follow this rule:

```text
Lightroom Classic
    owns descriptive photo keywords
            ↓
Exported JPEG
    carries IPTC/XMP keywords
            ↓
Flask
    imports keywords
            ↓
PostgreSQL
    stores photo-keyword relationships
            ↓
Website
    decides which keywords are primary categories
    and which are secondary filters
```

Keyword flow should remain **one-way from Lightroom to the website**.

Do not initially build bidirectional keyword synchronisation or a full website keyword editor.

### Reason for This Approach

This design:

- keeps Lightroom workflow simple
- avoids entering tags twice
- prevents separate Lightroom and website taxonomies drifting apart
- allows website navigation to change without retagging photographs
- allows many Lightroom keywords while exposing only a small curated set on the public site
- keeps website-specific presentation state separate from photographic metadata
